# Урок 31. Долговременная история запусков

## Цель

Агент уже умеет:

- хранить рабочее состояние внутри одного запуска;
- сохранять checkpoints графа;
- формировать итоговый `RunReport`;
- записывать JSON и Markdown отчёты.

Но после завершения нескольких запусков у системы пока нет единого источника,
из которого можно спросить:

```text
Сколько раз выполнялся этот test case?
Как завершился предыдущий запуск?
Были ли раньше успешные маршруты?
Какие ошибки повторяются?
```

В этом уроке создадим append-only историю завершённых запусков:

```text
RunReport
    -> RunHistoryRecord
    -> JsonlRunHistoryStore
    -> runs.jsonl
```

Это первый слой долговременной памяти агента.

## Карта видов памяти

Слово «память» в агентских системах используется для разных механизмов. Их нельзя
смешивать.

### 1. Working memory: `AgentState`

Содержит данные текущего выполнения:

```text
page_snapshot
proposed_action
route
step_count
failure_count
```

Она нужна planner, executor и другим нодам прямо сейчас.

Жизненный цикл:

```text
начало run -> изменения state -> конец run
```

### 2. Execution persistence: checkpoint

Checkpoint сохраняет:

- `AgentState`;
- позицию внутри LangGraph;
- следующую ноду;
- служебные данные выполнения.

Он нужен, чтобы остановить и продолжить один thread. Это техническое состояние
workflow, а не база знаний агента.

### 3. Episodic memory: run history

Эпизодическая память хранит факты о завершённых событиях:

```text
run-1: test login passed за 3 шага
run-2: test login failed из-за blocked button
run-3: test login passed после recovery
```

Каждый запуск является отдельным эпизодом. Именно этот слой мы реализуем сейчас.

### 4. Semantic memory: знания и RAG

Семантическая память содержит обобщённые или найденные знания:

```text
Для страницы login поле Username доступно по label.
Primary button иногда перекрывается banner-ом.
Для этого test case раньше работал маршрут fill -> fill -> click.
```

Такие знания позже будут извлекаться и передаваться planner. Но run history нельзя
автоматически считать истинными знаниями: старый маршрут мог быть ошибочным, сайт
мог измениться, а Judge мог дать неправильный verdict.

### 5. Feedback memory

Это человеческая разметка:

```text
предложенное действие было неправильным;
классификация должна быть product_bug;
этот маршрут подтверждён человеком;
этот отчёт нельзя использовать как пример.
```

Feedback добавит доверие и качество будущему RAG.

## Почему сначала сохраняем, а потом используем

Опасный подход:

```text
каждый старый run сразу добавить в prompt
```

Проблемы:

- prompt быстро растёт;
- модель получает нерелевантные маршруты;
- старые ошибки начинают повторяться;
- появляется feedback loop: ошибка модели становится подсказкой для модели;
- изменившийся UI делает старые действия устаревшими.

Production-последовательность:

```text
1. Сохранить сырые эпизоды.
2. Добавить метаданные и human feedback.
3. Научиться находить похожие эпизоды.
4. Отфильтровать недоверенные результаты.
5. Сформировать компактную подсказку.
6. Измерить, улучшилась ли evaluation.
```

Поэтому в уроке 31 история ещё не подключается к planner.

## Почему `RunReport`, а не `AgentState`

`AgentState` является внутренним mutable-контрактом workflow. Он содержит временные
поля:

```text
proposed_action
last_result
action_approval
```

Они могут меняться при рефакторинге графа.

`RunReport` является стабильной моделью завершённого результата:

```text
test_case
status
route
termination
verdict
classification
bug_report
```

Хранилище должно зависеть от стабильного доменного контракта, а не от внутреннего
словаря LangGraph.

## Зачем нужен `RunHistoryRecord`

Одного `RunReport` недостаточно. Один test case может выполняться много раз:

```text
test_case.id = login
run_id = login:550e8400...

test_case.id = login
run_id = login:73f47a10...
```

`test_case.id` отвечает:

> Какой сценарий выполнялся?

`run_id` отвечает:

> Какой конкретно запуск этого сценария мы рассматриваем?

Поле `recorded_at` позволяет строить временную последовательность.

```python
class RunHistoryRecord(BaseModel):
    run_id: str
    recorded_at: datetime
    report: RunReport
```

## Почему UTC и timezone-aware datetime

Плохое значение:

```python
datetime.now()
```

Оно не содержит timezone. При запуске worker-ов в разных регионах такие даты
невозможно надёжно сравнивать.

Используем:

```python
datetime.now(timezone.utc)
```

Пример:

```text
2026-06-23T09:15:00+00:00
```

Это timezone-aware UTC timestamp.

## Почему зависимости времени и ID можно внедрить

Production-код должен генерировать:

```python
uuid4()
datetime.now(timezone.utc)
```

Но тесты не должны зависеть от случайного UUID и текущей секунды. Поэтому функция
принимает необязательные значения:

```python
build_run_history_record(
    report,
    run_id="run-fixed",
    recorded_at=fixed_time,
)
```

Это простой dependency injection через параметры.

## Почему JSONL

Обычный JSON-массив:

```json
[
  {"run_id": "run-1"},
  {"run_id": "run-2"}
]
```

Чтобы добавить запись, обычно нужно:

1. прочитать весь файл;
2. распарсить массив;
3. добавить объект;
4. переписать весь файл.

JSON Lines хранит один объект на строку:

```json
{"run_id":"run-1", ...}
{"run_id":"run-2", ...}
```

Добавление выполняется через append:

```python
with path.open("a", encoding="utf-8") as file:
    file.write(record.model_dump_json() + "\n")
```

Преимущества:

- старые записи не переписываются;
- файл можно читать построчно;
- удобно импортировать в аналитические системы;
- одна запись соответствует одному событию.

Ограничения учебной реализации:

- нет блокировки concurrent writers;
- нет транзакций;
- поиск читает весь файл;
- нет индексов;
- повреждённая строка ломает чтение.

Для локального прототипа это нормально. В production этот же контракт можно
реализовать поверх PostgreSQL или event storage.

## Append-only как инженерный принцип

История запусков является журналом фактов. Старую запись не нужно незаметно
исправлять или удалять:

```text
run-1 failed
run-2 passed after prompt change
```

Если переписать `run-1` как passed, мы потеряем данные о регрессии и не сможем
оценить влияние изменения.

Исправления и feedback позже будут отдельными событиями, связанными через `run_id`.

## Задание 31.1. Построение записи

Реализуй `build_run_history_record()` в:

```text
src/browser_agent/run_history.py
```

Добавь импорты:

```python
from datetime import datetime, timezone
from uuid import uuid4
```

Правила:

1. Если `run_id` не передан, используй `str(uuid4())`.
2. Если `recorded_at` не передан, используй `datetime.now(timezone.utc)`.
3. Верни `RunHistoryRecord`.

Не используй:

```python
run_id = run_id or str(uuid4())
```

Пустая строка была передана явно и должна быть отклонена Pydantic как неправильное
значение. Проверяй именно `is None`.

## Задание 31.2. Append

Реализуй `JsonlRunHistoryStore.append()`:

1. Создай родительский каталог:

```python
self.path.parent.mkdir(parents=True, exist_ok=True)
```

2. Открой файл в режиме append:

```python
with self.path.open("a", encoding="utf-8") as history_file:
```

3. Запиши JSON одной строкой и завершающий `\n`.

Используй:

```python
record.model_dump_json()
```

Не используй `model_dump()`, потому что обычный dict всё ещё содержит `datetime`,
который стандартный `json.dumps()` не умеет сериализовать без дополнительной
настройки.

## Задание 31.3. Чтение

Реализуй `load_all()`:

1. Если файла нет, верни `[]`.
2. Прочитай файл построчно.
3. Игнорируй пустые строки.
4. Каждую строку восстанови:

```python
RunHistoryRecord.model_validate_json(line)
```

5. Верни записи в том же порядке, в котором они были добавлены.

Почему `model_validate_json`, а не `json.loads`:

- JSON парсится;
- вложенный `RunReport` восстанавливается;
- строки enum превращаются в enum;
- timestamp превращается в `datetime`;
- вся структура валидируется Pydantic.

## Задание 31.4. Запросы

Реализуй `find_by_test_case_id()`:

```text
load_all
-> оставить record.report.test_case.id == test_case_id
-> сохранить исходный порядок
```

Реализуй `latest_for_test_case()`:

1. Получи matching records.
2. Если список пуст, верни `None`.
3. Иначе верни последнюю запись.

В текущем контракте «latest» означает последнюю добавленную запись, а не запись с
максимальным `recorded_at`. Append order является порядком событий журнала.

## Что пока не делаем

В этом уроке намеренно отсутствуют:

- автоматическая запись из `run_agent`;
- изменение prompt planner;
- embeddings;
- vector database;
- similarity search;
- human feedback;
- удаление или редактирование истории;
- PostgreSQL.

Сначала реализуем и протестируем минимальный durable storage contract.
